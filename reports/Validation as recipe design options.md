# Make validation a recipe through key contributions

The most elegant design is option (c) in one specific form: **the core gains one generic, meaning-free primitive, a meta key that collects *contributions* and builds its single owning behavior from them, and the validation queue, `error`, `rule`/`asyncRule` and `validate()` all move into a recipe.** This "contributions → one owning behavior" mechanism (called c-contrib below) is not new machinery. It generalises the rule-only seam form-lib already ships (`RuleLike` / `RuleHooks` / `QueueChange`, plus the per-root-store `ValidationLayer`) into something any key can use. It keeps every current capability. Rules stay plain declarative list items in `defineBehaviors(shape, b => b.add(rule(...)))`, and `b.when`, `b.each`, late and component rules, row-local rules, one writer per target and `owner` all work unchanged. Reserving `error` in the core (option a) is not clearly more elegant, so by the author's own condition it should be rejected. It saves less than it appears, because the core needs the same in-place registration update under (a) once issue #15 moves async state into bindings. It also keeps `Rule` as a second declaration class, contradicts the author's founding "i don't hardcode within the library which meta fields exist", and hard-wires one team's policy (first error wins, sync before async, unchecked until forced) into the core. Every other recipe variant either loses a capability (static grouping, key-declared rules, multi-writer reducers) or pushes imperative registries and new entry points onto consumers (reconfigurable handles, install protocols). The recommendation costs one new public concept, an in-place update whose in-flight semantics must be specified, and a handful of generic `settle()` decisions that every option needs anyway.

## Every design must supply one reconfigurable writer per field

The question narrows quickly once the constraints are laid side by side. Several rules on one field all want to write `error`, and form-lib rejects two registrations with overlapping hosts and targets (`checkWriters`, [src/behaviors.ts:477-495](../src/behaviors.ts)). This is the author's own strict single-writer rule ("force user to make one way graph", [Claude conversation #24](../docs/02-claude-conversations.json)). So **some one registration must own each field's error**. Rules can also arrive after that registration exists: component rules via `useBehaviors`, rules added on a row store, rules inside `b.when`. Access is declared, and an undeclared read throws ([src/behaviors.ts:609-613](../src/behaviors.ts); [#15](https://github.com/TheAsda/form-lib/issues/15) decision 4), so a new rule's triggers and reads must be merged into the owner's declarations. **Some operation must therefore reconfigure a live registration.** Today that operation exists only privately for validation: `swap()` splits rules out, `ValidationLayer.change()` returns a `QueueChange`, and `apply()` commits it atomically with other registrations ([src/behaviors.ts:136-149, 323-381](../src/behaviors.ts); [src/validation.ts:231-268](../src/validation.ts)).

The agreed async decisions in [#15](https://github.com/TheAsda/form-lib/issues/15) sharpen this. Result reuse moves into `ctx.state`, which lives on the per-instance `Binding` ([src/behaviors.ts:239-260](../src/behaviors.ts)) and is transactional. In-flight runs are cancelled when their instance is disposed. Reconfiguring by *replacing* a registration would lose the checked-result cache and cancel running checks. Today's test "adding another rule keeps a checked result" ([src/validation.test.ts:294-303](../src/validation.test.ts)) only passes because the layer keeps async state in its own `WeakMap` outside the registration ([src/validation.ts:223](../src/validation.ts)). **After #15, every option needs an in-place registration update that preserves bindings, and that includes option (a).** This is the single most important fact for weighing (a): the core pays for the reconfiguration mechanism in any case. The only question is whether it stays validation-private or becomes generic.

Two semantic constraints complete the picture. First, a rule's `when` means "stop contributing, recompute without me", while a behavior's `when` means "skip the run, keep previous writes" ([src/builder.ts:14-21](../src/builder.ts); [src/behaviors.ts:635-637](../src/behaviors.ts)). A guarded rule therefore can never be modelled as a guarded behavior, or a stale error survives a guard turning false (pinned by [src/validation.test.ts:48-57](../src/validation.test.ts)). Second, the author has agreed that any rule registry is keyed per root store, which is already how the layer works: one `ValidationLayer` per `createStore`, with host filtering so that a rule added on a row applies to that row only ([src/validation.ts:221-225, 365](../src/validation.ts); [src/validation.test.ts:150-161](../src/validation.test.ts)). [#16](https://github.com/TheAsda/form-lib/issues/16) already records why "Rule extends Behavior" is not being done: it "breaks one writer per target, queue ordering, async ownership, and the different meaning of `when`." Any recipe design must respect that verdict rather than relitigate it.

## The author's history favours a recipe and parked the combiner idea

The founding Grok conversation framed validation as one behavior among several, not as a subsystem: "apply different behaviouslrs to the field such as some validations, calculations…" and, most emphatically, "**i don't hardcode within the library which meta fields exist**. They should be dynamic and inferrable… we just add it to metadata and we can handle it in the behavior" ([Grok #0, #2](../docs/01-grok-conversation.json)). The only textual hook for option (a) is the author's phrase "the default meta field 'error'" ([Grok #14](../docs/01-grok-conversation.json)). The same sentence puts `error` beside `touched` as "defaults" of "meta as a generic way to attach any value to a field". That reads as a conventional default on top of a generic mechanism, not a reserved core name. Grok's own sketch in that conversation silently had `required` and `uniqueEmail` both writing `error`, so one could erase the other ([Grok #21](../docs/01-grok-conversation.json)). The naive "each rule is a behavior" model was the starting point, and it does not work.

The Claude conversation shows how the queue arose. The assistant first proposed per-key **combiners**: `disabled`/`visible` any-of, and `error` as "the first non-empty contribution, in registration order" ([#23](../docs/02-claude-conversations.json)). The author found "the idea to have some logic for calculating meta if there are multiple sources… interesting" but asked for a strict single writer ([#24](../docs/02-claude-conversations.json)). The assistant agreed and **deferred combiners "as an addition we could make later for specific keys… Nothing else would have to change for that"** ([#25](../docs/02-claude-conversations.json)). The author then supplied the queue: rules "create a queue that is linked to the field's reference… apply validations till the first error" ([#26](../docs/02-claude-conversations.json)). The queue is a hard-coded combiner that is itself the single writer, which is exactly what c-contrib generalises. The same conversation also rejected a name-reserved `error` on principle before the core/recipe vocabulary existed. With plain `{ error: "" }`, "the runtime would have to treat the key name `error` as special… any field using `error` for its own purpose would suddenly get a validation queue". Features were introduced so "the key stays an ordinary name", and the author answered "it looks kinda like i wanted" ([#35, #36](../docs/02-claude-conversations.json)). The implementation then drifted back to literal `"error"` and `"validating"` strings ([src/validation.ts:282, 313-314](../src/validation.ts)). Option (a) would formalise that drift.

The author's other stated values point the same way. They asked for generic "async behavior functionality" ([#32](../docs/02-claude-conversations.json)), got async only for rules, and #15 now builds the generic version. They think of rules as behaviors ("put either one behavior/validation or the other", [#56](../docs/02-claude-conversations.json)). They want declarative rules as plain lists defined before React, with `useBehaviors` reusing the same builder ([#59-#61](../docs/02-claude-conversations.json)). Two things cut the other way and deserve honesty. [#20](https://github.com/TheAsda/form-lib/issues/20) records an earlier lean toward (a) ("the queue is mechanism and `error` is its output, not a policy"). And the author never directly compared "rule as behavior" with "rule as a separate kind" or took a position on warnings or the error type. `string | undefined` is an assistant default, so making `E` a recipe parameter overturns no author decision.

## Prior art reserves errors in forms but builds combining below them

Every mainstream form library surveyed keeps validation in its core with a reserved error slot: TanStack's `errorMap`/`errors`, Final Form's `error`, RHF's `formState.errors`, Formik's `errors`, Angular's `errors()` ([TanStack types.ts](https://github.com/TanStack/form/blob/555509cd941ae6ea3a2966ef3c879a322b3b383c/packages/form-core/src/types.ts#L536-L555); [Final Form FieldState](https://github.com/final-form/final-form/blob/2a5cc026c21d9487a403a1025dcea3e0f68f1dea/docs/types/FieldState.md); [RHF errors.ts](https://github.com/react-hook-form/react-hook-form/blob/3264a9b15beb86cdc73edadec4daa3fff1ec3aba/src/types/errors.ts#L20-L26)). **No surveyed library documents keeping `error` out of its core, so c-contrib is genuinely novel in this space.** That is the strongest steelman for (a). But those libraries have no core/recipe boundary to protect. Where a mature ecosystem does draw a mechanism/policy line, the combining mechanism sits below it and validation policy above it. Angular DI provides only `multi: true` ("multiple providers contribute values to the same token"), while `NG_VALIDATORS` and the rule "async validation… is performed only if the synchronous validation is successful" live in `@angular/forms` ([Angular DI](https://angular.dev/guide/di/defining-dependency-providers); [NG_VALIDATORS](https://angular.dev/api/forms/NG_VALIDATORS); [Angular form validation](https://angular.dev/guide/forms/form-validation)). Angular Signal Forms goes further: built-in constraint validators such as `required()` are implemented on a generic reducible metadata-key system, where "every time you call a validator, you're contributing to a metadata key" ([field-metadata guide](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/adev/src/content/guide/forms/signals/field-metadata.md)). Even there `errors` remains a dedicated channel, so the precedent is partial.

CodeMirror 6 facets are the closest structural match to c-contrib. A facet "is an extension point. Different extension values can provide values for the facet", and its definer supplies a `combine` function ([CodeMirror guide](https://codemirror.net/docs/guide/); [Facet.define](https://codemirror.net/docs/ref/#state.Facet%5Edefine)). Inputs are ordered by "explicitly set precedence category, and within that, by the position the extension has in the (flattened) collection", the facet object is the typed identity token, and facets exist so "multiple extensions that don't know anything about each other can be combined" ([Haverbeke, "Facets"](https://marijnhaverbeke.nl/blog/facets.html)). Mapped onto form-lib, the key definition is the facet, `contribute()` is `facet.of()`, and the key's combined behavior merges `combine` with `enables`. One owner per output then holds by construction. Token precedents (`InjectionToken`, `Facet`, `PluginKey`) also answer the "identity token" variant. form-lib's `MetaKeyDef` is already a frozen, typed object shared by every instance ([src/meta.ts:60](../src/meta.ts); [src/shape.ts:148-152](../src/shape.ts)), so it already *is* the token. A separate exported token adds nothing, and a `Symbol` key name is not viable because `.meta()` iterates `Object.entries` ([src/shape.ts:112-113](../src/shape.ts)).

The same survey argues against the other combining families. Multi-writer systems do not "just reduce". Kubernetes server-side apply needs recorded field managers, conflict errors and a force escape hatch ([Kubernetes SSA](https://kubernetes.io/docs/reference/using-api/server-side-apply/)), and Bevy needs explicit ordering plus ambiguity detection ([Bevy ScheduleBuildSettings](https://docs.rs/bevy/latest/bevy/ecs/schedule/struct.ScheduleBuildSettings.html)). The documented form-library bugs cluster in the same place. TanStack's `errorSourceMap` exists because form- and field-level validators share a slot, and it desyncs ([TanStack #2294](https://github.com/TanStack/form/issues/2294)). RHF 7.89.0 fixed stale form-level errors and stale results after `reset` ([RHF CHANGELOG](https://github.com/react-hook-form/react-hook-form/blob/3264a9b15beb86cdc73edadec4daa3fff1ec3aba/CHANGELOG.md)). form-lib's one-writer rule excludes that bug class, and a design that keeps it is worth more than one that relaxes it. Imperative reconfiguration (Angular's `addValidators` followed by a manual `updateValueAndValidity()`) works but makes "what is the current config?" a runtime question ([Angular form validation](https://angular.dev/guide/forms/form-validation)). CodeMirror's alternative, compartments that reconfigure through the normal update and keep state, is the declarative version c-contrib mirrors. Recipe-side grouping, as in Redux `combineReducers` or unified presets, is the simplest baseline. It breaks, however, when contributions are declared where the grouping call cannot see them ([Redux](https://redux.js.org/usage/structuring-reducers/beyond-combinereducers); [unified](https://github.com/unifiedjs/unified)).

## Thirteen designs, one survivor that stays clean

The table weighs every variant the research surfaced against the capabilities the current code and tests pin. "Late rule" means adding a rule to a field that already has rules, via `addBehavior` or `useBehaviors`. "Clean" means the core names no key and carries no validation policy.

The static and key-declared designs fail on concrete code paths. Registering a second queue for a field that already has one throws "already written by … – one writer per target" for root and row hosts alike ([src/behaviors.ts:481-490](../src/behaviors.ts)). Default behaviors built from key definitions may reference only their own node and are built once at `createStore` ([src/behaviors.ts:438-444, 689-703](../src/behaviors.ts)), which excludes cross-field rules such as `total` vs `requester.budget` in [examples/basic/src/form.ts:303-314](../examples/basic/src/form.ts) and every `b.when` guard on another field. The reducer design fails semantically. Every rule runs every time, so an async rule cannot be skipped when `required` fails. A false guard keeps the last write. A sibling rule's write would cancel an async rule under #15's "write from another origin cancels". The handle and install designs work, but they push a mutable per-store registry, host filtering, atomic multi-field updates and a React hook into recipe code that consumers copy. They also split the example's mixed lists ([examples/basic/src/form.ts:241-346](../examples/basic/src/form.ts)) into "behaviors go here, rules go through `addRules` there". Taken to its end, (e) rebuilds `RuleHooks`/`QueueChange` as a public API. That is c-contrib with a larger surface.

That leaves three serious contenders. **Option (a)** keeps everything working with the fewest new concepts, but it keeps roughly 300 post-#15 lines of validation policy in the core. It also keeps `Rule` beside `Behavior`, so #16's `instanceof Rule` branches ([src/builder.ts:77-91](../src/builder.ts); [src/react/behaviors.ts:61-101](../src/react/behaviors.ts)) remain, and it needs a glossary amendment. **Option (b′)** is the smallest diff and has the best typing, since `E` comes from the key ref. It also allows several queues per node, for example `error` plus `warning`. But its "capability" encodes first-error-wins, sync-before-async and unchecked-until-forced. That is precisely the policy that other libraries resolve differently: Angular Signal Forms and Formily collect all errors by default, and RHF's `criteriaMode: 'all'` exists for the same reason ([Signal Forms validation guide](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/adev/src/content/guide/forms/signals/validation.md); [Formily validator.ts](https://github.com/alibaba/formily/blob/d9a46442a575aa5f0fc1bd945e34d9a85d191d0e/packages/validator/src/validator.ts#L18-L38)). A choice that teams make differently is what the glossary means by a recipe's "one team's meaning". **c-contrib** is the only design that is glossary-clean, loses nothing, and changes no consumer call site beyond imports. It also delivers (b′)'s typing and multi-queue benefits, because the recipe owns the key type and can instantiate itself twice.

## Recommendation: keys that combine contributions into their owner behavior

The core gains two cooperating pieces, and each extends something that already exists. First, a meta key may declare `combine`, a sibling of today's `behavior` capability that reuses its machinery: per-instance default registrations flagged as feature writers, so `owner` keeps working. Unlike `behavior`, the factory receives the key's contributions and is re-invoked when they change. Second, `contribute(ref, payload, decl)` produces a `Contribution`, the second declaration class next to `Behavior`. Both share one `Declaration` (`name`, `triggers`, `reads`, `when`), which is what #16 was reaching for. The core never interprets a payload. It groups contributions per (root store, key), orders them by registration, filters them per instance by host store and guards, merges their declared refs into the owner's declarations, and hands the active list to `run`.

```ts
// ── core: src/meta.ts, src/behaviors.ts (sketch, names provisional) ──
export interface Declaration {
  name?: string;
  triggers?: readonly AnyRef[];
  reads?: readonly AnyRef[];
  when?: Guard | readonly Guard[];
}
export class Contribution<P = unknown> {
  constructor(readonly target: MetaRef<any, P>, readonly payload: P, readonly decl: Declaration) {}
}
export function contribute<P>(target: MetaRef<any, P>, payload: P, decl?: Declaration): Contribution<P>;

interface MetaKeyOptions<V, P = never> {
  // existing: owner, aggregate, inherit, reactive, keepOnReset, behavior
  /** Owner behavior built from the key's contributions. Mutually exclusive with `behavior`.
   *  Re-invoked when the contribution set changes; the registration is updated in place. */
  combine?: (self: any, parts: readonly Part<P>[]) => BehaviorConfig | undefined;
}
export interface Part<P> { readonly payload: P; readonly name: string }

// BehaviorContext of a combined owner:
//   ctx.parts: readonly Part<P>[]  — active for this instance, in registration order:
//   host store contains the instance, and every guard is true ("guard false = absent").
export type AnyBehavior = Behavior | Contribution;  // createStore, addBehavior, builder, useBehaviors
```

The validation recipe then owns every policy decision the core used to make: the error type, first-error ordering, sync before async, reuse of checked results, "async only on user edits unless forced", the hidden/disabled skip from [#21](https://github.com/TheAsda/form-lib/issues/21), and what `validate()` returns.

```ts
// ── recipe: recipes/validation.ts (copied and adapted by consumers) ──
type RulePart<E> =
  | { kind: "sync";  check: (v: any, ctx: RuleContext) => E | undefined }
  | { kind: "async"; check: (v: any, ctx: { signal: AbortSignal }) => Promise<E | undefined>;
      debounce?: number; origins?: "user" | "any" };

export const validation = <E = string>(o: { skip?: (self: any) => Guard[] } = {}) => ({
  error: metaKey<E | undefined, RulePart<E>>(undefined, {
    aggregate: (e) => e !== undefined,
    combine: (self, parts) => (parts.length ? queue<E>(self, parts, o.skip?.(self) ?? []) : undefined),
  }),
});

export const rule = <N extends WithKey<"error">>(n: N, check: RulePart<ErrorOf<N>>["check"], o?: RuleOptions) =>
  contribute(n.error, { kind: "sync", check }, o);            // o.triggers / o.reads / o.when → Declaration
export const asyncRule = /* same, kind: "async" */;
export const required = (n: WithKey<"error", string | undefined>) => rule(n, (v) => (isEmpty(v) ? "Required" : undefined));

function queue<E>(self: any, parts: readonly Part<RulePart<E>>[], skip: Guard[]): BehaviorConfig {
  return {
    name: `${self.path}#validation`,
    triggers: [self, ...skip.flatMap((g) => g.refs)],        // parts' own refs are added by the core
    writes: [self.error],
    async run(ctx) {
      if (skip.some((g) => !g.holds(ctx))) return ctx.set(self.error, undefined);  // skip clears, inside run
      const v = ctx.get(self);
      for (const p of ctx.parts) if (p.payload.kind === "sync") {
        const e = p.payload.check(v, ctx); if (e !== undefined) return ctx.set(self.error, e);
      }
      // async parts, in order until first error: reuse ctx.state.checked for identical inputs;
      // start only on user origin, origins: "any", or an explicit validate() request (open decision F5).
    },
  };
}

export async function validate(store: BaseStore<any>, node = store.node) {
  const { failures } = await store.settle(node, { rerun: true });   // generic core; see open decisions
  const errors = store.collect(node, "error");
  return { valid: errors.length === 0 && failures.length === 0, errors, failures };
}

// ── usage: unchanged apart from imports ──
export const behaviors = defineBehaviors(shape, (b, s) => {
  b.add(required(s.requester.email), email(s.requester.email),
        asyncRule(s.requester.email, checkEmployee, { debounce: 300 }));
  b.each(s.order.items, (b, item) => {
    b.when([item.sku], (sku) => !isEmpty(sku), (b) => b.add(required(item.qty)));
    b.add(min(item.qty, 1), calculate(item.lineTotal, [item.qty, item.unitPrice], mul));
  });
});
```

This design answers each constraint from the first section generically. Late and component rules re-combine the key inside the same transaction that today commits a `QueueChange`, so a rule added via `useBehaviors` joins an existing queue instead of throwing. Row-local rules work because the core already records each contribution's host and filters by it, so no public `store.contains()` is needed. The `when` asymmetry disappears as a special case. A guard on a behavior means "this declaration is inactive, so do not run", and a guard on a contribution means "this declaration is inactive, so it is absent from the owner's input". That is one rule with two natural readings, and the recipe never evaluates rule guards itself. Pending needs nothing: `pendingOf(node.error)` counts the owner's runs, so `validating` disappears as #15 intends. The payload type flows from the key (`MetaRef<V, P>`), much as `Facet<Input, Output>` types CodeMirror contributions, so contributing the wrong payload to a key is a compile error. Mixing is guarded as Angular guards multi and single providers. A combined key's owner is a feature registration, so an ordinary behavior writing `error` is rejected by today's `owner` check ([src/behaviors.ts:430-436](../src/behaviors.ts)), while program writes such as server errors stay allowed and persist until the next validation run, as [src/validation.test.ts:520-529](../src/validation.test.ts) requires.

The core change is mostly subtraction. `Rule`, `RuleLike`, `RuleHooks`, `ValidationLayer`, `Validatable`, `store.validate`/`_validation` and the literal strings `error`, `validating`, `visible` and `disabled` leave the core ([src/validation.ts](../src/validation.ts); [src/store.ts:688-694](../src/store.ts); [src/features.ts:29-36](../src/features.ts)). In their place come `Contribution`, `contribute`, the `combine` capability, `ctx.parts`, and the generalised grouping that is today's `ValidationLayer.change()` minus its rule-specific checks. The notes did not measure it, but the grouping should be a few dozen lines. The `instanceof Rule` branches in the builder and `useBehaviors` become `instanceof Contribution`, and #16 shrinks to "Behavior and Contribution share `Declaration`". `src/validation.test.ts` moves to the recipes project with its `validating` assertions rewritten as `pendingOf`, and core tests gain a small test-local combined key. **The in-place registration update is the one piece of real new engineering, and (a) needs it too.**

The costs are real. The core's public surface gains one concept, and it launches with only one confirmed user. Plausible second users exist but are unverified: OR-combining `disabled` so that `exclusive()` and `disableWhen()` stop conflicting on one field ([src/utilities.ts:217-231, 283-292](../src/utilities.ts)), a `warning` key built as a second instance of the recipe (Final Form documents warnings as exactly such a recipe, [react-final-form examples](https://github.com/final-form/react-final-form/blob/e09c3cf983bcce7721c6b9dfbbabee6fe62bf83c/docs/examples.md)), and a `required` meta OR-ed from several sources, as Angular does with `MetadataReducer.or()` ([metadata.ts](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/packages/forms/signals/src/api/rules/metadata.ts#L72-L120)). Because recipes are "copied and adapted, not depended on", roughly 200-300 lines of queue policy become consumer-owned code, and a fix to the queue no longer reaches every form automatically. The design is also novel among form libraries, so there is no field-tested precedent for its failure modes. Finally, no prototype yet confirms that the in-place update preserves `Binding` state cleanly once #15 lands, or that TypeScript infers `E` well through `metaKey<V, P>` and `rule(n, …)`. The typing risk matters because the author has abandoned designs before when inference broke ([Grok #38-#48](../docs/01-grok-conversation.json)).

## Seven decisions the design leaves open

Some decisions are not specific to c-contrib: removing the validation layer exposes them in every option, including (a), where they would stay hidden as private core behaviour. Others follow from the new mechanism. The table states each one with a suggested default.

| Decision | Why it is open | Suggested default |
|---|---|---|
| In-flight run when contributions change | #15 does not say whether an in-place update counts as disposal. Today a running check survives a rule change ([src/validation.ts:402-406](../src/validation.ts)). | Treat it like a `reads` change (#15 decision 7): cancel and rerun, keep `ctx.state`, so completed checks are reused and only a check running at that moment restarts |
| Forcing unchecked async (`validate()`) | `settle()` waits for runs but cannot start one the queue declined to start | Generic `settle(node, { rerun: true })` with `ctx.requested`. The alternative is a recipe-declared force key bumped in one `store.batch`, which needs no core change but adds a meta key per field |
| Failures | #15 routes a rejected run to `onError` and drops its writes, so `validate().failures` has no source | `settle()` returns the failed runs in the subtree. The alternative: the recipe catches, records and resolves |
| Per-rule debounce | #15 puts `debounce` on the behavior. A queue-level debounce would delay sync errors, and a timer inside `run` is not flushed by `settle()` | A `ctx.debounce(ms)` helper that `settle()` flushes. Otherwise a queue-level debounce computed from the async parts inside `combine` |
| Sync on init, async later | #15 decision 11 ("async runs don't start on creation") is ambiguous for a run that is sync at init and async later | Key the decision on the run, not the config: the queue returns sync on `ctx.isInit` |
| Ordering and dedup across modules | Registration order is asserted, not designed. VS Code needed explicit `order` because manifest order is not stable ([VS Code contribution points](https://code.visualstudio.com/api/references/contribution-points)) | Flattened declaration order now. Defer a `Prec`-style category and identity dedup until a real case appears |
| Glossary and debug surface | "Contribution" becomes a domain term, and scattered contributions need provenance | Add **Contribution** to GLOSSARY.md, and expose an ordered, per-key list of contributions with source names for dev tools |

Several recipe-level questions resolve themselves once validation is a recipe and need no core decision. The error type from [#12](https://github.com/TheAsda/form-lib/issues/12) becomes the recipe's `E`, with `{ kind, message? }` in the style of Angular Signal Forms as an i18n-friendly option. The skip seam from [#21](https://github.com/TheAsda/form-lib/issues/21) becomes a `validation({ skip })` argument evaluated inside `run`. Omission from [#22](https://github.com/TheAsda/form-lib/issues/22) moves into the submit recipe from [#19](https://github.com/TheAsda/form-lib/issues/19). What `ValidationResult` contains becomes each team's choice.

## Conclusion

The question first looked like "where does validation live", but the research shows it is really "who owns the one operation every design needs": reconfiguring a single writer as declarations arrive, without losing its state. form-lib already has that operation, built privately for validation and named `QueueChange`. Making it public and key-driven gives validation the same standing as any other meaning a team gives a key. It also delivers the author's founding promise that the library does not hard-code which meta keys exist, and it finally ships the combiner idea parked in #25 with the one-writer guarantee intact. Reserving `error` would buy a smaller diff today at the price of a core that keeps one team's validation policy forever, which fails the "clearly most elegant" bar.

The practical next step is a throwaway prototype. It should exercise three things before any refactor: the in-place update preserving `ctx.state` across a mid-flight rule addition, `E` and `P` inference through `metaKey` and `rule`, and one non-validation combined key (OR-ed `disabled`) to show the mechanism is not a disguised validation layer. If the prototype shows that the generic mechanism has no second user, or that inference collapses, the fallback should be (b′) rather than (a). It keeps the key recipe-named, keeps every call site, and leaves the queue's policy as the only compromise.
