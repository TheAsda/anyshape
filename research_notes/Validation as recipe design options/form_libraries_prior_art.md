## Q1. Is validation/error state in the core package or a separate package/plugin, and is the error key reserved?

### Takeaway
Every library surveyed has validation inside the core and a reserved, core-named error slot. None treats `error` as "just another metadata key a plugin writes". The closest to "validation built on generic mechanisms" are **Angular Signal Forms**, **Formily** and **Felte**. Angular builds constraint validators such as `required`/`min` and the async-validation resource on a generic reducible *metadata-key* system, but keeps `errors` as a separate dedicated channel. Formily stores a generic feedback list keyed by `(type, code, triggerType)`, and warnings/successes are just other `type`s. Felte takes validators and warning-validators from plugins ("extenders") through `addValidator`. Final Form's core also has a generic per-field `data` bag that its own docs use for a "warning engine" recipe.

### Cited Findings

**TanStack Form (`@tanstack/form-core` 1.33.5): core, reserved**
- Validation lives in `form-core` itself (`FieldApi.ts`, `FormApi.ts`, `ValidationLogic.ts`, `standardSchemaValidator.ts`). - Field meta has reserved keys `errorMap`, `errorSourceMap`, `errors`, `isValidating` (defaults `errors: []`, `errorMap: {}`, `errorSourceMap: {}`). — [types.ts#L536-L555](https://github.com/TanStack/form/blob/555509cd941ae6ea3a2966ef3c879a322b3b383c/packages/form-core/src/types.ts#L536-L555), [metaHelper.ts#L12-L21](https://github.com/TanStack/form/blob/555509cd941ae6ea3a2966ef3c879a322b3b383c/packages/form-core/src/metaHelper.ts#L12-L21)
- `errorMap` has fixed slots keyed by *validation cause*: `onMount`, `onChange`, `onBlur`, `onSubmit`, `onDynamic`, `onServer`. Async results share a slot with their sync counterpart (`onChange?: TOnChangeReturn | TOnChangeAsyncReturn`). — [types.ts#L64-L85](https://github.com/TanStack/form/blob/555509cd941ae6ea3a2966ef3c879a322b3b383c/packages/form-core/src/types.ts#L64-L85)

**Formily (2.3.7): core depends on a separate validator package; the feedback list is generic**
- `@formily/core` has a hard dependency on `@formily/validator` (same version), which holds the rule engine, the built-in rules/formats, and the locale/template registry. — [core/package.json](https://github.com/alibaba/formily/blob/d9a46442a575aa5f0fc1bd945e34d9a85d191d0e/packages/core/package.json); [validator/src/validator.ts](https://github.com/alibaba/formily/blob/d9a46442a575aa5f0fc1bd945e34d9a85d191d0e/packages/validator/src/validator.ts)
- The field stores one generic list `field.feedbacks: IFieldFeedback[]`. Each entry is `{ triggerType?, type?: 'error'|'success'|'warning', code?: 'ValidateError'|'ValidateSuccess'|'ValidateWarning'|'EffectError'|'EffectSuccess'|'EffectWarning'|string, messages?: any[] }`. — [core/src/types.ts#L121-L171](https://github.com/alibaba/formily/blob/d9a46442a575aa5f0fc1bd945e34d9a85d191d0e/packages/core/src/types.ts#L121-L171)

Different writers (the validator writes `Validate*` codes, user reactions/effects write `Effect*` codes via `field.selfErrors = [...]`) therefore occupy separate slots and do not overwrite each other. — [internals.ts#L274-L302](https://github.com/alibaba/formily/blob/d9a46442a575aa5f0fc1bd945e34d9a85d191d0e/packages/core/src/shared/internals.ts#L274-L302), [Field.ts#L355-L385](https://github.com/alibaba/formily/blob/d9a46442a575aa5f0fc1bd945e34d9a85d191d0e/packages/core/src/models/Field.ts#L355-L385)

**React Hook Form (7.89.0): core, reserved**

**Angular (`@angular/forms`): Reactive Forms (classic) and Signal Forms (v22)**
- Classic Reactive Forms: validators are part of `AbstractControl` in core. `control.errors: ValidationErrors | null`, where `ValidationErrors = {[key: string]: any}` is keyed by error name (for example `{required: true, minlength: {...}}`). Status is `'VALID'|'INVALID'|'PENDING'|'DISABLED'`. — [directives/validators.ts#L62](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/packages/forms/src/directives/validators.ts#L62), [abstract_model.ts#L60-L86](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/packages/forms/src/model/abstract_model.ts#L60-L86)
- Signal Forms (graduated to public API in v22): its core has a **generic metadata-key system**. `createMetadataKey<TWrite, TAcc>(reducer?)` and `metadata(path, KEY, logicFn)` let any number of schema rules contribute to a key, and the key's `MetadataReducer` combines them (`list`, `min`, `max`, `or`, `and`, `override`). Without a reducer the key uses "override" semantics (last contribution wins). — [metadata.ts#L33-L120, #L233-L260](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/packages/forms/signals/src/api/rules/metadata.ts#L33-L120); [field-metadata guide](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/adev/src/content/guide/forms/signals/field-metadata.md); [issue #68724 ("#68581 graduated Signal Forms APIs to public API")](https://github.com/angular/angular/issues/68724)
- Constraint validators are **built on metadata**. The guide says "Angular's built-in constraint validators like `required()` and `min()` use this system internally … every time you call a validator, you're contributing to a metadata key". `REQUIRED = createMetadataKey(MetadataReducer.or())`. `required()` writes a private memo key and `REQUIRED`, then calls `validate()` to produce the error. — [field-metadata.md#L3](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/adev/src/content/guide/forms/signals/field-metadata.md), [metadata.ts#L328](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/packages/forms/signals/src/api/rules/metadata.ts#L328), [required.ts#L41-L60](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/packages/forms/signals/src/api/rules/validation/required.ts#L41-L60)
- `validateAsync` is also built on metadata. It creates a *managed* metadata key (`createManagedMetadataKey`) that owns a `Resource` built from params, writes params into it via `metadata()` (or `undefined` to skip), and then registers an async error rule that maps the resource status to `'pending'` or errors. — [validate_async.ts#L128-L180](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/packages/forms/signals/src/api/rules/validation/validate_async.ts#L128-L180)
- **Errors themselves are not metadata.** `validate()` calls `pathNode.builder.addSyncErrorRule(...)` and async uses `addAsyncErrorRule`, a dedicated channel. The guide notes that "Non-constraint validators like `email()` and `validate()` do not contribute to metadata". Field state exposes reserved `errors()`, `pending()`, `valid()`, `invalid()`, `errorSummary()`. — [validate.ts#L33-L42](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/packages/forms/signals/src/api/rules/validation/validate.ts#L33-L42), [field-metadata.md#L54](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/adev/src/content/guide/forms/signals/field-metadata.md), [field/validation.ts#L40-L130](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/packages/forms/signals/src/field/validation.ts#L40-L130)
- Validation is skipped automatically for hidden, disabled or readonly fields (`shouldSkipValidation`). — [field/validation.ts#L129-L132](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/packages/forms/signals/src/field/validation.ts#L129-L132)

### Inferences
- The industry default is "core reserves `error(s)`". No mainstream library lets the core be ignorant of errors. The designs closest to form-lib's goal are:
  1. **Angular Signal Forms**: a generic reducible metadata-key system in core, with constraint validators *and* the async-validation resource implemented on top of it. Errors are still a special channel with core-owned `valid`/`pending` semantics. This is strong prior art that "multiple contributors per key + reducer" works in practice, and that even Angular did not fold `errors` into the generic metadata channel.
  2. **Formily**: one generic "feedback" collection where `type` (error/warning/success) is data, and each writer gets its own slot keyed by `code` (plus `triggerType`). Validity is a derived query (`errors.length === 0`). This amounts to "error is just a tag on a message".
  3. **Final Form `data` + mutator**: a generic per-field bag that plugins write. The official docs build a warning engine on it (see Q5), but real errors still use the reserved channel because submit-blocking and `valid` are core concepts.
- Across libraries, the core tends to own validity (`valid`, `invalid`, `pending`/`validating`, submit gating), even when error *messages* are generic. If form-lib moves `error` out of core, something still has to define "submit is blocked while X", and that is probably the real piece to design.
- TanStack's `errorSourceMap` is a symptom of *not* having exactly-one-writer per slot: form-level and field-level validators both write `errorMap.onChange`, so the core had to bolt on a provenance map to decide who clears what, and it has had bugs from the two maps desynchronising (see Q8).

### Gaps
- I did not read Formily's documentation site (core.formilyjs.org) for stated rationale. The findings come from source only.
- I did not verify the exact Angular release number that first shipped Signal Forms as stable. The source is annotated `@publicApi 22.0`, and issue #69620 says "Signal Forms are new in v22".

## Q2. How are many validators per field declared and combined (order, first-error vs all, sync vs async, field vs form, merging)?

### Takeaway
There are three families. The first is **one validator function per event slot**, where composition is the user's problem: TanStack, RHF `validate`, Formik, Conform. The second is an **ordered list with first-error short-circuit**: Formily with `validateFirst`, Modular Forms, vee-validate with `bails` (default true), RHF by default (`criteriaMode: 'firstError'`). The third is **run everything and merge/concatenate**: Angular classic (merge of the error map; a later validator overrides the same key), Angular Signal Forms (list, no short-circuit), Felte and Formik (deep-merge). Field-level vs form-level precedence is nearly always "**field-level wins**" (TanStack, Final Form, Modular Forms), or form-level *replaces* field-level entirely (RHF `resolver`, vee-validate form `schema`). Async generally runs only after sync passes.

### Cited Findings

**TanStack Form**
- There is one function (or Standard Schema) per cause: `validators: { onMount, onChange, onChangeAsync, onBlur, onBlurAsync, onSubmit, onSubmitAsync, onDynamic, onDynamicAsync }` on both field and form. It does not accept arrays. — [FieldApi.ts#L307](https://github.com/TanStack/form/blob/555509cd941ae6ea3a2966ef3c879a322b3b383c/packages/form-core/src/FieldApi.ts#L307), [validation guide](https://tanstack.com/form/latest/docs/framework/react/guides/validation)
- Sync runs first, and async runs only if sync did not error, unless `asyncAlways: true`. — [FieldApi.ts#L1679](https://github.com/TanStack/form/blob/555509cd941ae6ea3a2966ef3c879a322b3b383c/packages/form-core/src/FieldApi.ts#L1679), [validation.md "asyncAlways"](https://github.com/TanStack/form/blob/555509cd941ae6ea3a2966ef3c879a322b3b383c/docs/framework/react/guides/validation.md)
- A form-level validator can return `{ form: ..., fields: { 'a.b': err } }` to target fields. For merging at field level, "we prioritize the field level error": if the field's own validator returns an error it wins, otherwise the form error is used, and the slot is tagged `'field'`/`'form'` in `errorSourceMap`. At form level, a new form error overwrites. A stale form-sourced error is cleared, but a field-sourced error is kept. — [utils.ts#L556-L612](https://github.com/TanStack/form/blob/555509cd941ae6ea3a2966ef3c879a322b3b383c/packages/form-core/src/utils.ts#L556-L612); the docs state the form error "may be overwritten by the field-specific validation" ([validation guide](https://tanstack.com/form/latest/docs/framework/react/guides/validation))
- Across causes, `errors` is the flattened concatenation of all `errorMap` slots, so an `onChange` error and an `onBlur` error coexist. — [custom-errors.md "disableErrorFlat"](https://github.com/TanStack/form/blob/555509cd941ae6ea3a2966ef3c879a322b3b383c/docs/framework/react/guides/custom-errors.md)
- Cross-field re-validation is declared on the field: `onChangeListenTo` / `onBlurListenTo: DeepKeys[]`. — [FieldApi.ts#L226, #L249](https://github.com/TanStack/form/blob/555509cd941ae6ea3a2966ef3c879a322b3b383c/packages/form-core/src/FieldApi.ts#L226)
- `revalidateLogic({ mode, modeAfterSubmission })` is a pluggable *validation-timing* strategy (the `onDynamic` cause), a small example of a replaceable policy object. — [ValidationLogic.ts#L46-L60](https://github.com/TanStack/form/blob/555509cd941ae6ea3a2966ef3c879a322b3b383c/packages/form-core/src/ValidationLogic.ts#L46-L60)

**Formily**
- `field.validator` is `Validator = ValidatorDescription | ValidatorDescription[]`. Each description is a format string, a function `(value, rule, ctx, render) => string | boolean | {type, message} | Promise<...>`, or a rules object (`required`, `pattern`, `max`, `minLength`, `format`, `validator`, `message`, `triggerType`, ...). — [validator/src/types.ts#L17-L111](https://github.com/alibaba/formily/blob/d9a46442a575aa5f0fc1bd945e34d9a85d191d0e/packages/validator/src/types.ts#L17-L111)
- `validate()` awaits each parsed rule **sequentially in array order**. Every result is pushed into `results[type]` (error/warning/success), and the loop breaks on the first message only if `validateFirst` is set. So the default is **collect all**. — [validator.ts#L18-L38](https://github.com/alibaba/formily/blob/d9a46442a575aa5f0fc1bd945e34d9a85d191d0e/packages/validator/src/validator.ts#L18-L38)
- Each rule has its own `triggerType` (default `'onInput'`). Validation for a trigger runs only the rules for that trigger, and results are stored per trigger in `feedbacks`. — [parser.ts#L146-L147](https://github.com/alibaba/formily/blob/d9a46442a575aa5f0fc1bd945e34d9a85d191d0e/packages/validator/src/parser.ts#L146), [internals.ts#L305-L326](https://github.com/alibaba/formily/blob/d9a46442a575aa5f0fc1bd945e34d9a85d191d0e/packages/core/src/shared/internals.ts#L305-L326)
- `setValidatorRule(name, value)` edits a rule in place if present. Otherwise it appends the rule, except `required`, which is *prepended* so it runs first. — [internals.ts#L328-L349](https://github.com/alibaba/formily/blob/d9a46442a575aa5f0fc1bd945e34d9a85d191d0e/packages/core/src/shared/internals.ts#L328-L349)
- Sync and async are not distinguished. Everything is awaited in one sequential pipeline.

**Final Form**
- Each `registerField(name, subscriber, subscription, { getValidator })` call adds a validator under that subscriber's index (`field.validators[index] = getValidator`). Several `<Field>` components with the same name therefore contribute several validators. — [FinalForm.ts#L995](https://github.com/final-form/final-form/blob/2a5cc026c21d9487a403a1025dcea3e0f68f1dea/src/FinalForm.ts#L990-L996)
- All field validators run, and the first synchronous non-empty result in registration order wins ("first registered validator wins"). Async results are applied when they resolve. — [FinalForm.ts#L346-L400](https://github.com/final-form/final-form/blob/2a5cc026c21d9487a403a1025dcea3e0f68f1dea/src/FinalForm.ts#L346-L400)
- For record vs field level, "field-level errors take precedent over record-level errors" (`fieldLevelError || asyncRecordLevelError || recordLevelError || errorFromParent`). — [FinalForm.ts#L478-L495](https://github.com/final-form/final-form/blob/2a5cc026c21d9487a403a1025dcea3e0f68f1dea/src/FinalForm.ts#L478-L495)
- `validateFields?: string[]` on a field limits which other fields re-validate when it changes. — [docs/types/FieldConfig.md](https://github.com/final-form/final-form/blob/2a5cc026c21d9487a403a1025dcea3e0f68f1dea/docs/types/FieldConfig.md)

**React Hook Form**
- A field has fixed built-in rules plus `validate: fn | Record<string, fn>`, so several named custom validators are possible. Evaluation is built-ins first, then `validate` (in object key order). It returns on the first error unless `validateAllFieldCriteria` (`criteriaMode: 'all'`), in which case every failing rule is collected into `error.types: Record<type, message | message[]>`. — [validateField.ts#L38, #L243-L300](https://github.com/react-hook-form/react-hook-form/blob/3264a9b15beb86cdc73edadec4daa3fff1ec3aba/src/logic/validateField.ts#L243-L300), [types/form.ts#L64, #L135](https://github.com/react-hook-form/react-hook-form/blob/3264a9b15beb86cdc73edadec4daa3fff1ec3aba/src/types/form.ts#L135)
- A `resolver` **replaces** built-in/register validation: `executeBuiltInValidation` only runs when `!_options.resolver`, and the form-level `validate` only when `!resolver && validate`. — [createFormControl.ts#L268-L280, #L1352-L1363](https://github.com/react-hook-form/react-hook-form/blob/3264a9b15beb86cdc73edadec4daa3fff1ec3aba/src/logic/createFormControl.ts#L1352-L1363)
- Asked in 2020 to allow resolver and register rules together (#1674), the maintainer replied it "was considered and investigated, but it difficult to implement and decided to keep as it is". — [issue #1674](https://github.com/react-hook-form/react-hook-form/issues/1674)
- `ValidateForm` receives `{ formValues, formState, eventType, name }` and returns `Record<field, {message, type}> | string | boolean`. — [types/validator.ts#L43-L54](https://github.com/react-hook-form/react-hook-form/blob/3264a9b15beb86cdc73edadec4daa3fff1ec3aba/src/types/validator.ts#L28-L54)

**Angular Reactive Forms (classic)**
- A control has `validators: ValidatorFn[]` and `asyncValidators: AsyncValidatorFn[]`. `compose` runs **all** sync validators and shallow-merges their `ValidationErrors` objects (`{...res, ...errors}`), so a later validator with the same key overwrites. `composeAsync` runs all async validators in parallel with `forkJoin` and merges. — [validators.ts#L623-L712](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/packages/forms/src/validators.ts#L623-L712)
- Async validators run only when sync status is VALID. — [abstract_model.ts#L1403-L1413](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/packages/forms/src/model/abstract_model.ts#L1403-L1413)
- Group/array validators put errors on the *group's* `errors`, not the children's. The long-open issue #10530 "Expose FormControl errors to parent FormGroup" (30 comments) shows the pain of the opposite direction. — [issue #10530](https://github.com/angular/angular/issues/10530)
- `setErrors()` manual errors "are always overwritten by the results of the next validation run". — [abstract_model.ts#L1477-L1484](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/packages/forms/src/model/abstract_model.ts#L1477-L1484)

**Angular Signal Forms**
- Rules are declared in a schema function: `required(p.x)`, `email(p.x)`, `validate(p.x, fn)`, `validateTree`, `validateAsync`, `validateHttp`, `validateStandardSchema`, with `applyWhen`/`applyWhenValue`/`applyEach` for conditional and array cases. "All validation rules run on every change - validation doesn't short-circuit after the first error". — [validation.md#L45-L53](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/adev/src/content/guide/forms/signals/validation.md)
- Async "Only runs after all synchronous validation rules pass". `validateAsync` writes `undefined` params when `!syncValid()`. — [validation.md#L717-L718](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/adev/src/content/guide/forms/signals/validation.md), [validate_async.ts#L147-L157](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/packages/forms/signals/src/api/rules/validation/validate_async.ts#L147-L157)
- Tree validators and async validators can *target* errors at other fields (`fieldTree` on the error). Otherwise the error goes to the validated field. — [validate_async.ts#L24-L36](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/packages/forms/signals/src/api/rules/validation/validate_async.ts#L24-L36)
- Constraint metadata from several rules is combined by the key's reducer, for example `REQUIRED` with `or()` and min/max with `min()`/`max()` reducers. — [metadata.ts#L72-L120](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/packages/forms/signals/src/api/rules/metadata.ts#L72-L120)

**Brief**
- Modular Forms: `validate: MaybeArray<ValidateField>`. Validators run sequentially with `await`, and the loop breaks on the first error. Then `fieldError = localError || formErrors[name] || ''`, so field-level wins over form-level. — [methods/validate.ts#L135-L147](https://github.com/fabian-hiller/modular-forms/blob/7bc44f3d18fd05a344d83183a5c3204fb6bb1ba9/packages/solid/src/methods/validate.ts#L135-L147)
- vee-validate: field `rules` can be a function, an array of functions ("pipeline"), a rule string/object, or a Standard Schema. The pipeline runs sequentially and returns early when `bails` is true, which is the default. If the form has a `schema`, the field's own rules are ignored (`validator` computes to `undefined`). — [validate.ts#L93-L120](https://github.com/logaretm/vee-validate/blob/7d8cc524f9204655ad00a466090738e43b44ff2a/packages/vee-validate/src/validate.ts#L93-L120), [useField.ts#L110-L114](https://github.com/logaretm/vee-validate/blob/7d8cc524f9204655ad00a466090738e43b44ff2a/packages/vee-validate/src/useField.ts#L110-L114)
- Felte: `validate` and `warn` each accept a function or an array of functions (form-level). All run, and results are deep-merged with array-concatenation of messages (`mergeErrors`). — [types.ts#L281-L283](https://github.com/pablo-abc/felte/blob/ab1ae409ec99d36fa08a8cbe1a8de4e2fda84ccf/packages/common/src/types.ts#L281-L283), [executeValidation.ts#L20-L41](https://github.com/pablo-abc/felte/blob/ab1ae409ec99d36fa08a8cbe1a8de4e2fda84ccf/packages/common/src/utils/executeValidation.ts#L20-L41)
- Formik: field-level `validate` (from `<Field validate>`), `validationSchema` and form `validate` all run in parallel and are combined with `deepmerge.all([fieldErrors, schemaErrors, validateErrors])`. — [Formik.tsx#L310-L321](https://github.com/jaredpalmer/formik/blob/91475adbf33579561e580eceea0c031f4ec2e992/packages/formik/src/Formik.tsx#L310-L321)
- Conform: one `onValidate` or schema per form, with no field-level validators. A sync schema result can be post-processed by `onValidate`, but "The "onValidate" handler is not supported when used with asynchronous schema validation". — [future/forms.tsx#L401-L420](https://github.com/edmundhung/conform/blob/da874d94824ba6b3b45623d6e430f88c6366c538/packages/conform-react/future/forms.tsx#L401-L420)

### Inferences
- form-lib's current design (sync rules in order until the first error, then async, per-field queue) matches the Modular Forms / vee-validate `bails` / RHF `firstError` family. The Formily, Angular Signal Forms and RHF `criteriaMode: 'all'` behaviour ("collect all") is the common alternative, so a recipe could expose first-error vs all as a reducer choice.
- Two implementations already show that reducer-per-key composition can express validation combination:
  - Angular's `MetadataReducer`, which has `list()`, `or()`, `min()`, `max()` and `override()`.
  - Formily's upsert-by-`code`.

  In both, "many rules from different places write the same key" becomes "each rule contributes, and a declared reducer folds the contributions". That fits form-lib's "exactly one writer per target" constraint if each contributor writes its *own* sub-slot and one reducer behavior writes the final `error`.
- "Field-level beats form-level" is the dominant precedence rule (TanStack, Final Form, Modular Forms). The alternative, form-level schema replaces field rules (RHF resolver, vee-validate schema), is a documented source of user friction (RHF #1674).

### Gaps
- I found no primary-source rationale from TanStack maintainers for why each cause accepts a single function rather than an array. Issue #75 ("Multiple validation on field", 2019) predates the current architecture and was not about arrays.

## Q3. How is async validation cancelled and debounced, and how is "pending" represented?

### Takeaway
TanStack is the only library with both a real `AbortSignal` passed to validators and built-in per-cause debounce. Angular classic cancels by unsubscribing from the Observable. Angular Signal Forms uses Resources with a per-validator `debounce` option. Final Form, RHF, vee-validate and Modular Forms only *ignore stale results* (via a counter, call-id or latest-promise check) and have no abort and no built-in debounce. Standard Schema has no AbortSignal in its `validate` options.

### Cited Findings
- **TanStack**: validators receive `signal: AbortSignal`. Before a new run the previous `lastAbortController.abort()` is called, and debounce is `asyncDebounceMs` (field/form) with per-cause overrides `onChangeAsyncDebounceMs`, `onBlurAsyncDebounceMs`, `onDynamicAsyncDebounceMs`, implemented with `setTimeout` that checks `controller.signal.aborted`. The pending state is `isValidating`, driven by a counter of in-flight validations. — [FieldApi.ts#L116, #L222-L264, #L1378-L1405, #L1497-L1540](https://github.com/TanStack/form/blob/555509cd941ae6ea3a2966ef3c879a322b3b383c/packages/form-core/src/FieldApi.ts#L1497-L1540)
- **Angular classic**: `_cancelExistingSubscription()` unsubscribes the previous async validator Observable on every `updateValueAndValidity`. Status becomes `PENDING` while running. There is no built-in debounce, and the idiomatic approach is `timer(ms).pipe(switchMap(...))` inside the validator, which works because unsubscription cancels the timer. — [abstract_model.ts#L1443-L1475](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/packages/forms/src/model/abstract_model.ts#L1443-L1475). Issue #9119 "Control Validators should be observable chains" is still open. — [issue #9119](https://github.com/angular/angular/issues/9119)
- **Angular Signal Forms**: `validateAsync({ params, factory, onSuccess, onError, debounce?, when? })`, where `debounce` is "Duration in milliseconds to wait before triggering the async operation, or a function that returns a promise". Cancellation and staleness are handled by Angular `Resource` semantics (params change leads to reload). A `'pending'` sentinel sits in `asyncErrors`, and "The `valid()` signal returns `false` while validation is pending … `invalid()` only returns `true` if errors exist" (three-state validity). — [validate_async.ts#L74-L80, #L128-L180](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/packages/forms/signals/src/api/rules/validation/validate_async.ts#L128-L180), [validation.md#L730](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/adev/src/content/guide/forms/signals/validation.md)
- Angular also has a separate field-level `debounce(path, ms | 'blur')` rule that delays UI-to-model sync, and therefore *all* validation. A user expected it to debounce only async validation (#65641). A team member (per the reporter's relay) said "debounce of async validation is a separate thing". — [debounce.ts#L30](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/packages/forms/signals/src/api/rules/debounce.ts#L30), [issue #65641](https://github.com/angular/angular/issues/65641)
- **Final Form**: no abort. Per-field `asyncValidationKey` increments per run, and a result is applied only if the key still matches ("Only apply error if this validation hasn't been superseded"). The form-level `nextAsyncValidationKey` does the same for record-level validation. Field `validating` is a per-field counter, and form `validating` is a count. — [FinalForm.ts#L353-L390, #L546-L548](https://github.com/final-form/final-form/blob/2a5cc026c21d9487a403a1025dcea3e0f68f1dea/src/FinalForm.ts#L353-L390)
- **RHF**: no AbortSignal and no validation debounce. Staleness is handled with call-ids (`_setValidCallId`, `_resetCallId`). 7.89.0 (2026-09-26) fixed "Stale validation results … being applied after `reset`". `delayError` delays *displaying* errors, not running validation. — [createFormControl.ts#L268-L273, #L1361-L1367](https://github.com/react-hook-form/react-hook-form/blob/3264a9b15beb86cdc73edadec4daa3fff1ec3aba/src/logic/createFormControl.ts#L1361-L1367), [CHANGELOG 7.89.0](https://github.com/react-hook-form/react-hook-form/blob/3264a9b15beb86cdc73edadec4daa3fff1ec3aba/CHANGELOG.md)
- **vee-validate**: `withLatest(fn, onDone)` discards results from all but the latest run, with no abort. `meta.pending` shows the pending state. — [utils/common.ts#L251-L269](https://github.com/logaretm/vee-validate/blob/7d8cc524f9204655ad00a466090738e43b44ff2a/packages/vee-validate/src/utils/common.ts#L251-L269), [useField.ts#L174-L192](https://github.com/logaretm/vee-validate/blob/7d8cc524f9204655ad00a466090738e43b44ff2a/packages/vee-validate/src/useField.ts#L174-L192)
- **Formily**: I found no abort or debounce code in `@formily/core` or `@formily/validator` (grep for abort/debounce returned nothing). `validating` is a boolean set around `validateSelf`. — [internals.ts#L944-L990](https://github.com/alibaba/formily/blob/d9a46442a575aa5f0fc1bd945e34d9a85d191d0e/packages/core/src/shared/internals.ts#L944-L990)
- **Felte**: a hand-rolled cancellable signal (`{aborted, priority}`) where "Keeping a controller allows us to cancel previous asynchronous validations". It also has a `debounced: { validate, warn, timeout, validateTimeout, warnTimeout }` config. — [core/src/stores.ts#L30-L45, #L203-L230](https://github.com/pablo-abc/felte/blob/ab1ae409ec99d36fa08a8cbe1a8de4e2fda84ccf/packages/core/src/stores.ts#L203-L230), [types.ts#L279-L291](https://github.com/pablo-abc/felte/blob/ab1ae409ec99d36fa08a8cbe1a8de4e2fda84ccf/packages/common/src/types.ts#L279-L291)
- **Conform `future`**: an `AbortController` per submission/validation: "cancel the previous request if a new one is made", and it also aborts on unmount. — [future/hooks.tsx#L262-L266, #L370-L425](https://github.com/edmundhung/conform/blob/da874d94824ba6b3b45623d6e430f88c6366c538/packages/conform-react/future/hooks.tsx#L420-L425)
- **Standard Schema**: `validate(value, options?: { libraryOptions? })` has no AbortSignal. Issue #42 "Question about interruption of async validation" is open. The spec author said to wait "once at least two popular schema libraries support this feature", and Effect/schema was cited as one. — [spec/src/index.ts#L48-L66](https://github.com/standard-schema/standard-schema/blob/6fafde5d4e8372937793c92092322a15b6e711cd/packages/spec/src/index.ts#L48-L66), [issue #42](https://github.com/standard-schema/standard-schema/issues/42)

### Inferences
- form-lib's "debounced, abortable per-field queue" is at parity with TanStack, the most capable of the group. Angular Signal Forms shows the same features expressed *per validator* (each `validateAsync` owns its resource, debounce and `when`) rather than per field. That is a natural fit if validation becomes a recipe of independent behaviors.
- Because Standard Schema cannot receive a signal, any abort must be implemented around it (ignore stale results). A recipe wrapping Standard Schema can only discard stale results. It cannot actually cancel the work.
- Angular's `valid()` vs `invalid()` asymmetry (pending counts as not valid but also not invalid) is a precise, documented semantics worth copying if pending moves into a recipe.

### Gaps
- I did not check whether Formily's React/Vue bindings add debounce at the component layer.

## Q4. How are error types made generic (strings vs objects vs i18n)?

### Takeaway
There are two camps. The first is **opaque/generic**: TanStack (`ValidationError = unknown`, any truthy value is an error, per-cause type inference), Final Form (`any`), Conform (`ErrorShape` generic, default `string[]`). The second is **structured with a discriminator**: Angular (`ValidationErrors` map keyed by error name; Signal Forms `ValidationError { kind, message? }`), RHF (`FieldError { type, message }`), Formily (`{ type, message }` plus a template/locale registry). String-only libraries (Modular Forms, vee-validate, Formik, Standard Schema `Issue.message: string`) push i18n into message generation (vee-validate `@vee-validate/i18n`, Formily `registerValidateLocale`).

### Cited Findings
- **TanStack**: `export type ValidationError = unknown`. "the library allows you to return any type of value from your validators … any truthy value is considered an error". `errorMap.onBlur` is typed from the return type of the `onBlur` validator, with 9 or more generic parameters per field (`TOnMount`, `TOnChange`, `TOnChangeAsync`, …, `TFormOnChange`, …). — [types.ts#L35](https://github.com/TanStack/form/blob/555509cd941ae6ea3a2966ef3c879a322b3b383c/packages/form-core/src/types.ts#L35), [custom-errors.md#L6-L8, #L255-L275](https://github.com/TanStack/form/blob/555509cd941ae6ea3a2966ef3c879a322b3b383c/docs/framework/react/guides/custom-errors.md)
- For Standard Schema validators, TanStack stores the `StandardSchemaV1Issue[]` array as the error. Source TODOs note that `disableErrorFlat` typing for issues (`StandardSchemaV1Issue[][]`) is unfinished. — [types.ts#L360-L366](https://github.com/TanStack/form/blob/555509cd941ae6ea3a2966ef3c879a322b3b383c/packages/form-core/src/types.ts#L355-L370)
- **Angular classic**: `ValidationErrors = {[key: string]: any}`, keyed by error name with arbitrary payload (for example `minlength: {requiredLength, actualLength}`), and not type-safe. Issue #47911 "Typed ValidatorFn and AsyncValidatorFn for typed forms" is open. — [directives/validators.ts#L62](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/packages/forms/src/directives/validators.ts#L62), [issue #47911](https://github.com/angular/angular/issues/47911)
- **Angular Signal Forms**: `interface ValidationError { readonly kind: string; readonly message?: string }`, extended as `WithFieldTree` to carry the target field. Built-ins set `kind` ('required', 'email', 'minLength'…), and "The `message` property is optional", so i18n is done by mapping `kind` to text in the template. — [validation_errors.ts#L368-L408](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/packages/forms/signals/src/api/rules/validation/validation_errors.ts#L368-L408), [validation.md#L370-L376](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/adev/src/content/guide/forms/signals/validation.md)
- **RHF**: `FieldError.type: LiteralUnion<keyof RegisterOptions, string>`, `message?: Message` where `Message = string`. `types?: MultipleFieldErrors` holds all criteria when `criteriaMode: 'all'`. — [types/errors.ts#L12-L32](https://github.com/react-hook-form/react-hook-form/blob/3264a9b15beb86cdc73edadec4daa3fff1ec3aba/src/types/errors.ts#L12-L32)
- **Formily**: a validator returns `string | boolean | {type, message}`. Messages come from rule `message` or `getValidateLocale(ruleName)`, rendered through a pluggable template engine (`registerValidateMessageTemplateEngine`) with `setValidateLanguage`/`registerValidateLocale`. `FeedbackMessage = any[]`, so custom effect messages can be anything. — [validator/src/types.ts#L17-L40](https://github.com/alibaba/formily/blob/d9a46442a575aa5f0fc1bd945e34d9a85d191d0e/packages/validator/src/types.ts#L17-L40), [registry.ts#L66-L120](https://github.com/alibaba/formily/blob/d9a46442a575aa5f0fc1bd945e34d9a85d191d0e/packages/validator/src/registry.ts#L66-L120), [core/src/types.ts#L142](https://github.com/alibaba/formily/blob/d9a46442a575aa5f0fc1bd945e34d9a85d191d0e/packages/core/src/types.ts#L142)
- **Final Form**: field `error: any`. Record-level errors are an object mirroring the values shape, with `FORM_ERROR` and `ARRAY_ERROR` symbols-as-keys for non-leaf errors. — [FieldState.md](https://github.com/final-form/final-form/blob/2a5cc026c21d9487a403a1025dcea3e0f68f1dea/docs/types/FieldState.md), [docs/api.md](https://github.com/final-form/final-form/blob/2a5cc026c21d9487a403a1025dcea3e0f68f1dea/docs/api.md)
- **Conform**: `FormError<ErrorShape = string[]>`, and the `future` API's `ErrorShape = any` generic flows from schema/validator to field metadata. — [conform-dom/types.ts#L19](https://github.com/edmundhung/conform/blob/da874d94824ba6b3b45623d6e430f88c6366c538/packages/conform-dom/types.ts#L19), [future/types.ts#L203-L233](https://github.com/edmundhung/conform/blob/da874d94824ba6b3b45623d6e430f88c6366c538/packages/conform-react/future/types.ts#L203-L233)
- **String-only**: Modular Forms `ValidateField` returns `MaybePromise<string>`. vee-validate `GenericValidateFunction` returns `boolean | MaybeArray<string>`, and `@vee-validate/i18n` interpolates `{field}`-style templates. Formik errors are `string` leaves. — [modular-forms field.ts#L57-L60](https://github.com/fabian-hiller/modular-forms/blob/7bc44f3d18fd05a344d83183a5c3204fb6bb1ba9/packages/solid/src/types/field.ts#L57-L60), [vee-validate forms.ts#L146-L149](https://github.com/logaretm/vee-validate/blob/7d8cc524f9204655ad00a466090738e43b44ff2a/packages/vee-validate/src/types/forms.ts#L146-L149), [vee-validate i18n](https://github.com/logaretm/vee-validate/tree/7d8cc524f9204655ad00a466090738e43b44ff2a/packages/i18n/src), [formik types.tsx#L14](https://github.com/jaredpalmer/formik/blob/91475adbf33579561e580eceea0c031f4ec2e992/packages/formik/src/types.tsx#L14-L22)
- **Standard Schema**: `Issue { message: string; path?: (PropertyKey | {key})[] }`. There is no code/kind field, so an adapter from issues to i18n-keyed errors cannot recover a machine-readable reason in a portable way. — [spec/src/index.ts#L65-L85](https://github.com/standard-schema/standard-schema/blob/6fafde5d4e8372937793c92092322a15b6e711cd/packages/spec/src/index.ts#L65-L85)

### Inferences
- If `error` stops being a core key, the error *type* naturally becomes a recipe type parameter: a recipe instance declares its key as `MetadataKey<E>`, like Angular's `createMetadataKey<TWrite, TAcc>`. That avoids the TanStack cost of threading many generic parameters through the field type.
- `{ kind, message? }` (Angular Signal Forms) is the most i18n-friendly *default* shape with an optional message. Standard Schema's `message: string` forces string errors at the interop boundary unless the vendor puts a code in `message`.

### Gaps
- I did not verify how TanStack types the errors of a form-level Standard Schema when mapped onto individual fields (only the TODO comments were read).

## Q5. Are non-blocking warnings supported?

### Takeaway
First-class warnings exist in **Formily** (feedback `type: 'warning'`, which does not affect `valid`) and **Felte** (a separate `warnings` store, `warn` validators, `addValidator(fn, {level:'warning'})`). **Final Form** documents warnings as a *recipe* built from subscriptions plus the `setFieldData` mutator. TanStack, RHF, Angular (both APIs), Modular Forms, vee-validate, Formik, Conform and Standard Schema have no warnings. In TanStack the documented workaround (`{ message, level: 'warning' }`) is still counted as an error, because any truthy value is invalid.

### Cited Findings
- **Formily**: `IValidateResult.type: 'error' | 'warning' | 'success' | string`. `validate()` returns `{error:[], warning:[], success:[]}`. `valid` is computed from errors only. There are `field.warnings`, `selfWarnings` and `setSelfWarnings`. — [validator/src/types.ts#L17-L27](https://github.com/alibaba/formily/blob/d9a46442a575aa5f0fc1bd945e34d9a85d191d0e/packages/validator/src/types.ts#L17-L27), [Field.ts#L296-L324, #L369-L400](https://github.com/alibaba/formily/blob/d9a46442a575aa5f0fc1bd945e34d9a85d191d0e/packages/core/src/models/Field.ts#L296-L324)
- **Felte**: `warn?: ValidationFunction | ValidationFunction[]` ("Optional function to set warnings based on the current state of your data"), `level?: 'warning' | 'error'` on `addValidator`, and separate debounce timeouts for warn. — [types.ts#L181-L190, #L279-L291](https://github.com/pablo-abc/felte/blob/ab1ae409ec99d36fa08a8cbe1a8de4e2fda84ccf/packages/common/src/types.ts#L181-L191)
- **Final Form / react-final-form**: the official examples list "Field Warnings: Demonstrates how the power of subscriptions and mutators can be used to build a warning engine: logic to display a message next to each field that is _not_ an error (thus it does _not_ prevent form submission)". — [react-final-form docs/examples.md#L95-L99](https://github.com/final-form/react-final-form/blob/e09c3cf983bcce7721c6b9dfbbabee6fe62bf83c/docs/examples.md), [codesandbox](https://codesandbox.io/s/m5qwxpr6o8)
- **TanStack**: the docs example returns `{ message: 'Missing uppercase', level: 'warning' }` to show custom error shapes, but the same page says "any truthy value is considered an error and will mark the form or field as invalid". — [custom-errors.md#L8, #L225-L245](https://github.com/TanStack/form/blob/555509cd941ae6ea3a2966ef3c879a322b3b383c/docs/framework/react/guides/custom-errors.md)
- **Standard Schema**: issue #89 "Can we add optional IssueType to the spec?" (error vs warnings, plus a proposed `WarningResult` with both `value` and `issues`) is open with no maintainer commitment. — [issue #89](https://github.com/standard-schema/standard-schema/issues/89)
- **Angular Signal Forms**: grep over `packages/forms/signals/src` found no warning or severity concept. The metadata guide suggests using a `list()` reducer key when "multiple validation rules … each contribute a hint". — [field-metadata.md#L165-L198](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/adev/src/content/guide/forms/signals/field-metadata.md)

### Inferences
- Warnings are the clearest case where "validation as recipe on generic metadata" pays off. Final Form's official answer *is* a recipe on a generic per-field data bag, and Angular's guide recommends a `list()`-reduced metadata key for hints. If the validation recipe is parameterised by output key and "blocks submit?", a warning is just a second instance of it writing to a `warning` key.
- Formily's model (severity as a field on each message plus a derived `valid`) is the alternative "single collection" design. It needs a core notion of which severities block.

### Gaps
- I could not open the Final Form "Field Warnings" codesandbox for code-level details (only the example description in the repo docs).
- I found no GitHub issue or discussion in the TanStack, RHF or Angular repos where maintainers explicitly accept or reject warnings. My GitHub searches returned no relevant hits.

## Q6. Can validators be added dynamically (e.g. on component mount) or only up front?

### Takeaway
Dynamic, mount-scoped validators are common. They appear in Final Form (every `registerField` subscriber contributes one, and it is removed on unregister), TanStack (validators live in field options set by the mounted `<Field>`), Formik (`<Field validate>` registers into a map), RHF (`register(name, rules)` at mount), Angular classic (`addValidators`/`removeValidators`/`hasValidator` imperatively), Formily (`setValidator`/`setValidatorRule`, plus effects/reactions), and Felte (`addValidator` from extenders). Angular Signal Forms is the exception: rules are declared once in the schema function, and dynamism is expressed *reactively* with `applyWhen`, `when:` and signal-valued schemas, not by adding or removing rules.

### Cited Findings
- Final Form keys validators by subscriber index: `state.fields[name].validators[index] = fieldConfig.getValidator`. `getValidator` is a thunk re-read on each run, so the latest function from a re-rendered component is used. — [FinalForm.ts#L333-L344, #L990-L996](https://github.com/final-form/final-form/blob/2a5cc026c21d9487a403a1025dcea3e0f68f1dea/src/FinalForm.ts#L333-L344)
- TanStack field validators are part of `FieldApiOptions.validators`, and `field.update(opts)` refreshes options from the component on render. — [FieldApi.ts#L307, #L990](https://github.com/TanStack/form/blob/555509cd941ae6ea3a2966ef3c879a322b3b383c/packages/form-core/src/FieldApi.ts#L990). Known pain: conditionally rendered fields and submit validation (#1874, open), and `onMount` field errors never reaching the field (#1366, open). — [issue #1874](https://github.com/TanStack/form/issues/1874), [issue #1366](https://github.com/TanStack/form/issues/1366)
- Angular classic: `addValidators(validators)`, `removeValidators`, `hasValidator` (removal compares by reference), `setValidators`, then `updateValueAndValidity()`. — [abstract_model.ts#L815-L946](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/packages/forms/src/model/abstract_model.ts#L847-L946)
- Angular Signal Forms: conditional rules via `when` (e.g. `required(p.x, { when })`), `applyWhen`, `applyWhenValue`, and a signal-valued Standard Schema ("You can pass a signal instead of a static schema so the validation schema updates automatically"). — [validation.md#L130-L141, #L649-L654, #L752-L780](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/adev/src/content/guide/forms/signals/validation.md), [structure.ts#L353](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/packages/forms/signals/src/api/structure.ts#L353)
- Formily: `field.setValidator(v)` and `field.setValidatorRule(name, value)` at runtime. `field.validator` is observable, so reactions and effects can change it. — [Field.ts#L405-L411](https://github.com/alibaba/formily/blob/d9a46442a575aa5f0fc1bd945e34d9a85d191d0e/packages/core/src/models/Field.ts#L405-L411), [internals.ts#L328-L349](https://github.com/alibaba/formily/blob/d9a46442a575aa5f0fc1bd945e34d9a85d191d0e/packages/core/src/shared/internals.ts#L328-L349)
- Felte: `addValidator: AddValidatorFn` is exposed to extenders. — [types.ts#L192-L221](https://github.com/pablo-abc/felte/blob/ab1ae409ec99d36fa08a8cbe1a8de4e2fda84ccf/packages/common/src/types.ts#L192-L221)
- Formik: `registerField(name, { validate })` from `<Field>`/`useField`. — [Formik.tsx#L536](https://github.com/jaredpalmer/formik/blob/91475adbf33579561e580eceea0c031f4ec2e992/packages/formik/src/Formik.tsx#L536)
- RHF: rules passed to `register` at mount, with `shouldUnregister` and `_removeUnmounted` cleaning up. — [createFormControl.ts#L925](https://github.com/react-hook-form/react-hook-form/blob/3264a9b15beb86cdc73edadec4daa3fff1ec3aba/src/logic/createFormControl.ts#L925)

### Inferences
- Final Form's "every subscriber may contribute a validator, keyed by subscriber id, first non-empty wins" is the closest existing model to "many rules from different places, added when components mount, combined into one field error". It is effectively a per-field multi-writer slot with a fixed reducer (first-wins).
- Angular Signal Forms shows the other extreme: static declaration with reactive conditions. That makes rule composition deterministic (schema order) and avoids mount-order-dependent results. Final Form's "first *registered* wins" is mount-order dependent.

### Gaps
- I did not examine how Final Form orders validators after unregister and re-register (index reuse).

## Q7. Standard Schema as a validation interop layer

### Takeaway
Standard Schema (`@standard-schema/spec` 1.1.0) is a tiny structural interface (`~standard.validate(value, options?) => Result | Promise<Result>`, issues with `message` and `path`). TanStack, vee-validate 5, Angular Signal Forms and Conform `future` consume it natively. It has no issue code/kind, no severity, and no AbortSignal, and each gap has an open issue.

### Cited Findings
- Interface: `StandardSchemaV1.Props { version: 1; vendor: string; validate(value: unknown, options?: { libraryOptions? }): Result<Output> | Promise<Result<Output>>; types? }`. `FailureResult { issues: ReadonlyArray<Issue> }` and `Issue { message: string; path?: ReadonlyArray<PropertyKey | { key }> }`. 1.1.0 also adds `StandardTypedV1` and `StandardJSONSchemaV1`. — [spec/src/index.ts](https://github.com/standard-schema/standard-schema/blob/6fafde5d4e8372937793c92092322a15b6e711cd/packages/spec/src/index.ts#L1-L90), [standardschema.dev](https://standardschema.dev/)
- Consumers:
  - TanStack: "natively supports all libraries following the Standard Schema specification". — [validation guide](https://tanstack.com/form/latest/docs/framework/react/guides/validation)
  - vee-validate 5.0.0-beta.0: "implement standard schema". — [CHANGELOG](https://github.com/logaretm/vee-validate/blob/7d8cc524f9204655ad00a466090738e43b44ff2a/CHANGELOG.md)
  - Angular: `validateStandardSchema(path, schema | () => schema)`. — [standard_schema.ts#L70](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/packages/forms/signals/src/api/rules/validation/standard_schema.ts#L70)
  - Conform: `future/standard-schema.ts`. — [conform future](https://github.com/edmundhung/conform/tree/da874d94824ba6b3b45623d6e430f88c6366c538/packages/conform-react/future)
- Known integration pain: in Angular, `validateStandardSchema` + `validateHttp` on the same field tree threw NG0992 (resource-in-resource), reported against v22 (#69620, closed). — [issue #69620](https://github.com/angular/angular/issues/69620)
- Open spec gaps: abort (#42) and issue severity/type (#89). — [issue #42](https://github.com/standard-schema/standard-schema/issues/42), [issue #89](https://github.com/standard-schema/standard-schema/issues/89)

### Inferences
- A Standard Schema is naturally *form-level or subtree-level* and returns path-addressed issues. Using it as a per-field rule source requires splitting issues by `path` into per-field contributions, which is exactly what TanStack's form-level `{ fields }` mapping and Angular's tree-targeted errors do. In a recipe design that becomes one "schema" behavior writing contributions for many fields.

### Gaps
- None significant.

## Q8. Documented rationale and known pain points about these choices

### Takeaway
Few libraries publish an explicit rationale for putting validation in the core. The pain points documented in issues cluster around four themes:
1. Multiple writers to one error slot: TanStack's `errorSourceMap` desyncs, RHF stale form-level errors.
2. Inability to combine validation sources: RHF resolver plus rules (#1674).
3. Async staleness after reset: RHF 7.89.0.
4. Debounce scope confusion: Angular #65641.

Angular Signal Forms' metadata guide is the most explicit design rationale for reducer-based combination.

### Cited Findings
- TanStack #2294 (open): `setFieldValue` "clears errorMap.onMount but leaves errorSourceMap.onMount stale", so "the two maps can end up out of sync". This is a direct cost of a parallel provenance map. — [issue #2294](https://github.com/TanStack/form/issues/2294)
- TanStack #1366 (open): "Field validation errors returned by the `onMount` validator never make it to the Field instance". — [issue #1366](https://github.com/TanStack/form/issues/1366)
- TanStack #2129 (open): "Newly pushed array fields do not show form-level errors on submit while existing errors remain". — [issue #2129](https://github.com/TanStack/form/issues/2129)
- RHF 7.89.0 fixed "Form-level validation leaving stale errors after a successful re-validation", "Form-level `validate` running a stale function", and "Stale validation results (resolver, built-in, form-level `validate`) being applied after `reset`". — [CHANGELOG 7.89.0](https://github.com/react-hook-form/react-hook-form/blob/3264a9b15beb86cdc73edadec4daa3fff1ec3aba/CHANGELOG.md)
- RHF #1674: resolver and rules together were rejected as "difficult to implement". — [issue #1674](https://github.com/react-hook-form/react-hook-form/issues/1674)
- Angular metadata guide on why reducers exist: "Override semantics work when only one rule contributes to a key … As soon as two rules contribute, the first value is silently discarded … This is almost never what you want. Contributions often come from different sources: two schemas composed with `apply()` … or multiple validation rules that each contribute a hint." — [field-metadata.md#L165-L180](https://github.com/angular/angular/blob/b6bf6504adab1a78cc62ad8402f6bed229e620bd/adev/src/content/guide/forms/signals/field-metadata.md)
- Angular #65641: the field `debounce()` rule delays all validation, not just async. The team's view was that async-validation debounce "is a separate thing" (now `validateAsync({debounce})`). — [issue #65641](https://github.com/angular/angular/issues/65641)
- Angular classic long-standing issues: #9119 (validators as observable chains, open), #10530 (child errors exposed to parent, open), #47911 (typed validator functions, open). — [#9119](https://github.com/angular/angular/issues/9119), [#10530](https://github.com/angular/angular/issues/10530), [#47911](https://github.com/angular/angular/issues/47911)
- Final Form's rationale for resolving (not rejecting) async errors: "The reason it _resolves_ with errors is to leave _rejection_ for when there is a server or communications error." — [docs/types/Config.md#validate](https://github.com/final-form/final-form/blob/2a5cc026c21d9487a403a1025dcea3e0f68f1dea/docs/types/Config.md)

### Inferences
- Most of the recorded bugs are of one kind: more than one writer to a single error slot (form vs field vs mount vs submit vs server), plus stale async writes. form-lib's "exactly one writer per target" rule rules out that class by construction. A validation recipe that has each rule source write its own contribution key, with one combiner behavior as the only writer of the final `error`, keeps that guarantee. This mirrors Angular's contribution-plus-reducer model and Formily's upsert-by-`code`.
- No surveyed library documents a decision to keep `error` *out* of core, so moving it out would be novel. The nearest precedents are Final Form's warning recipe and Angular's metadata-backed constraint validators, and in both the "blocking" error channel stays special.

### Gaps
- I found no maintainer-authored design document from TanStack, RHF or Formily explaining why validation is a core concept. Discussion searches returned only usage questions.
