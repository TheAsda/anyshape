# Recipes

Recipes give meta keys one meaning (what `error` holds, when it shows, what `disabled` implies, what submitting does) on top of the core's public interface. The core gives no key a meaning, so a form needs recipes for validation, input state and submit.

The package ships one set, the **default recipes**, as two entries: `anyshape/recipes` and, for React, `anyshape/recipes/react`. Nothing in `anyshape/recipes` imports React. There are two ways to use them:

- **Import them as they are.** Validation, input state, submit and focus work with no code to copy. [`POLICIES.md`](POLICIES.md) lists every decision they make for you (when an error shows, what counts as empty, what a submit does), so you can judge whether they fit before you depend on them.
- **Copy the whole set and change it,** when your forms need another policy. The recipes have no options: changing a policy means editing a copy ([Customizing: copy the whole set](#customizing-copy-the-whole-set)).

Each recipe imports only `anyshape`, the React ones also `anyshape/react`, and the rest of the set by a relative path. That is what lets a copy work against the installed package unchanged. To write a recipe of your own, read [Writing your own recipe](../docs/guide/writing-a-recipe.md) in the guide.

## The catalog

| File                                     | What it gives you                                                                                                                                                                                                                                                                                                                                                                                      | Keys it defines                                                                                                                                                                                                                                                                                                                                                |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [`validation.ts`](validation.ts)         | `rule` and `asyncRule` for a field's checks, and `validate(store, node)`, which checks a subtree and lists its errors. A field's sync rules run in order until one fails; its async rules run after them, with optional debounce, and their results are reused while the inputs are unchanged. `InferChecked<N>`, the node's value once its checks pass: no `undefined` where `defined()` is declared. | `errorKey` (combined, counted: the first failing rule's message), `checkForcedKey` (set by `validate`), `requiredNowKey` (combined: true while a `required` rule is present, for the UI), `definedKey` (its default contributes a "Required" check to `error` while the value is `undefined`, after the sync rules). Meta groups: `validation()`, `defined()`. |
| [`rules.ts`](rules.ts)                   | Ready rules: `required`, `minLength`, `maxLength`, `min`, `max`, `pattern`, `email`, and `exclusive` (at most, or exactly, one of several fields filled). `isEmpty`, what they count as empty. Each states in its type what kind of node it accepts.                                                                                                                                                   | None; they contribute to `error`, `required` also to `requiredNow`, and `exclusive` also to `disabled`.                                                                                                                                                                                                                                                        |
| [`control.ts`](control.ts)               | The keys an input needs, and `control()`, which declares them.                                                                                                                                                                                                                                                                                                                                         | `editedKey` (counted: set by the user's first edit), `dirtyKey` (counted: differs from the baseline), `revealedKey` (set on blur and by a submit). Meta groups: `edited()`, `dirty()`, `revealed()`, and `control()` = `validation()` + `edited()` + `dirty()` + `revealed()`.                                                                                 |
| [`visibility.ts`](visibility.ts)         | `visibleWhen`, which computes `visible` both ways.                                                                                                                                                                                                                                                                                                                                                     | `visibleKey`. Meta group: `visible()`.                                                                                                                                                                                                                                                                                                                         |
| [`disabling.ts`](disabling.ts)           | `disableWhen`, one reason for `disabled`.                                                                                                                                                                                                                                                                                                                                                              | `disabledKey` (combined: true while any reason applies). Meta group: `disabled()`.                                                                                                                                                                                                                                                                             |
| [`values.ts`](values.ts)                 | Value behaviors: `calculate` (a derived value), `link` (two values kept in step both ways), `clearWhen` (a value reset to its baseline while a test holds).                                                                                                                                                                                                                                            | None.                                                                                                                                                                                                                                                                                                                                                          |
| [`submit.ts`](submit.ts)                 | `handleSubmit(store, fn)`: reveals every error, validates, waits for async checks, then calls `fn` with the value as it is, typed as its checked type (`InferChecked`), or focuses the first error. One submit at a time per store. A section with `submitting()` is submittable, so a step's Next is `handleSubmit(store.substore(step), fn)`.                                                        | `submittingKey`. Meta group: `submitting()`.                                                                                                                                                                                                                                                                                                                   |
| [`focus.ts`](focus.ts)                   | `registerFocus(store, node, target)` and `focusFirst(entries)`. The pattern for state kept beside the form: focus targets are DOM handles, so they live in the recipe's own registry, not in the store.                                                                                                                                                                                                | None.                                                                                                                                                                                                                                                                                                                                                          |
| [`react/control.ts`](react/control.ts)   | `useControl(node)`: an input's binding for a node with `control()`, one object holding the value, `onChange`, `onBlur`, the control keys, `pending`, `showError` and `focusRef`. Destructure it: the React compiler lint flags `c.focusRef` beside other reads of `c`.                                                                                                                                 | None; reads the `control()` keys.                                                                                                                                                                                                                                                                                                                              |
| [`react/adapters.ts`](react/adapters.ts) | `fromInput` and `fromCheckbox`: turn an `onChange` for values into a DOM change handler.                                                                                                                                                                                                                                                                                                               | None.                                                                                                                                                                                                                                                                                                                                                          |

`index.ts` is `anyshape/recipes` and `react/index.ts` is `anyshape/recipes/react`; each lists the entry's exports. Every meta key is declared through a meta group (`field<string>().meta(control(), defined())`), and its definition, with a `Key` suffix, is what a sweep or a count takes (`countIn(shape, errorKey)`); see [ADR 0007](https://github.com/TheAsda/anyshape/blob/master/docs/adr/0007-keys-are-declared-through-meta-groups.md).

## Policies

[`POLICIES.md`](POLICIES.md) lists every policy the default recipes hold: what they do, the main alternative, why the default was picked, and where to change it in a copy. A change to any of them is a breaking change of the package, released as one, so an upgrade never changes how your forms behave without saying so.

## Customizing: copy the whole set

1. Copy the recipes out of your installed package, `node_modules/anyshape/recipes/`, into your project, for example as `src/forms/recipes/`. They are the `.ts` sources of the version you run. Copy all of them, even the ones you won't change.
2. Switch every import from `anyshape/recipes` and `anyshape/recipes/react` to your copy, in one change. Your form code stays the same apart from those import paths.
3. Make your change. [`POLICIES.md`](POLICIES.md) says where each policy lives. Rename what you like: keys are found by their definitions, never by name, so a node can declare `edited` as `wasEdited` and every helper still finds it.
4. If you want to keep your copy tested, copy the recipes' tests too. They aren't in the package: take `recipes/test/` from the repository at the release tag of your version (`https://github.com/TheAsda/anyshape/tree/v<version>/recipes/test`). They use [Vitest](https://vitest.dev); the React tests run in browser mode with `vitest-browser-react`. The same tag also holds the sources, if you'd rather copy from there.

**Don't mix the default recipes with a copy.** Keys are matched by their definitions, and a copy's definitions are its own. A recipe that sweeps a subtree only sees its own set's keys: on a form declared with the shipped `control()`, a copied `validate` finds no `error` key and reports an invalid form as valid, and a copied `handleSubmit` throws that the node doesn't declare `submitting()`. Nothing fails to compile, because both sets' nodes have the same shape. So a form uses the default recipes or one copy, and a move to a copy moves every import at once.

After you copy, an upgrade of the package no longer changes your recipes. The changelog marks every change to a default recipe, so you can bring the ones you want into your copy.

The repository's lint (`bun run lint`, the boundary rules in [`.oxlintrc.json`](https://github.com/TheAsda/anyshape/blob/master/.oxlintrc.json)) checks that the recipes import only the public entries, and the package check compiles the shipped sources, copied unchanged, against the packed package.
